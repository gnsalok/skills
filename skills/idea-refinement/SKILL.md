# Idea refinement

Find a worthwhile problem and the smallest way to learn whether the proposed
solution helps. The outcome is a decision brief, not production code.

## Ground the idea

Read the user's context and available product/repository evidence. Identify the
person affected, their current task or workaround, the friction, and why it
matters. Separate observations from beliefs. If “user” describes several groups,
choose the group this iteration serves and record the others as out of scope.

Ask only questions that change the direction: the desired outcome, a hard
constraint, or a contradictory requirement. Retrieve repository facts yourself.
For an interview request, explore unresolved decisions in short rounds; do not
force a questionnaire when the context already supplies the answers.

## Explore and narrow

Compare a few materially different approaches, including improving the existing
workflow or doing nothing when appropriate. For each, explain the value, hardest
assumption, implementation/operating effort, and failure condition. Avoid ranking
options with invented user research or precise scores unsupported by evidence.

Challenge whether the requested feature addresses the actual problem. A request
for a dashboard may be a need to notice failures sooner; an email digest or one
useful alert may test that need more cheaply. Preserve user constraints rather
than expanding the idea into a platform.

## Produce a decision brief

Return the problem, target audience, recommended direction and reasoning,
alternatives, non-goals, assumptions, and smallest useful scope. Include one
experiment with a success signal, failure signal, and evidence needed to decide.
Mark proposed targets as proposed, and distinguish a recommendation from a choice
the user has made. “Do not build yet” can be the right recommendation.

Save the brief if requested, following existing project conventions. The next
stage can turn the chosen direction into acceptance criteria. Completion means
the reader can decide what to test or specify next, without treating unresolved
assumptions as requirements.
